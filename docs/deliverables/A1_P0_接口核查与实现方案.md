### 1.5 MuJoCo 并发边界（决定场景应用是否安全）

【源码证实】

- MuJoCo 在**独立物理线程**中步进，持 `physics_thread_mutex_`
  （`mujoco_ros/src/physics.cpp:86–98`；`mj_step` 在 :121/:185/:239）。
- 控制器 `read()`/`write()` **不在另一个线程**：它们由 `mjcb_control`/`mjcb_passive`
  在 `mj_step` **内部**回调（`mujoco_env.cpp:250–251`、`:512–522` →
  `mujoco_ros2_control.cpp:98–112`），因此与步进天然串行。
- `franka_hardware/src/sim/franka_mj_hardware_system.cpp` 内**没有任何 mutex**：
  `write()` 中的 `std::lock_guard<std::mutex> guard(mj_mutex_);` 在 **:356 已被注释掉**，
  且 `mj_mutex_` 成员**并不存在**。
- `/grasp_weld_active` 订阅回调（同上 :188–195）只写一个 `std::atomic<bool>`
  `weld_active_desired_`（:192）；真正的 weld 开关在 `write()` 的 :494–518 内完成。
  回调线程是 `FrankaExecutor`（MultiThreadedExecutor，自有线程），但因为只碰原子量，是安全的。

⇒ **结论（对 A1 至关重要）**：
一个 ROS 回调若**直接**改 `d_->qpos`（例如把杆摆到采样位姿），**会与 `mj_step` 竞争**，
而 `franka_mj_hardware_system.cpp` 里没有任何锁可以保护它。
**必须**走 `mujoco_ros` 的 `set_body_state` 服务，因为 `interface.cpp:260` 显式取了
`physics_thread_mutex_`。这是当前唯一被证实安全的写入路径，也是 §4.3 方案的基础。

## 2. 任务从何处取杆位姿：逐阶段的实际取值

### 2.1 三个“取位姿”入口（全部是同一个通道）

【源码证实】任务节点只有**一条**杆位姿输入通道：`/detected_rod_pose`。

- `carry_task_state_machine.cpp:54` 声明参数 `use_vision`（默认 `false`）。
- `:80–93` **仅当 `use_vision_ == true`** 时才创建 `/detected_rod_pose` 订阅。
- `carry_task_context.hpp:79–85, 110–131` 保存 `detected_rod_pose_` / `rod_pose_received_`，
  读写由 `rod_pose_mutex_` 保护。
- 三处“回退链”本质相同：先用 `getDetectedRodPose()`，失败则用硬编码。

| 使用点 | 行号 | 有检测位姿时 | 无检测位姿时（Mode A 的实际情况） |
|---|---|---|---|
| `executeApproach` 取 `obj_x/obj_y` | `dual_arm_controller.cpp:969–972` | `detected.x/y` | **硬编码 `0.50 / 0.0`** |
| `publishAluminumRod` 的 box_pose | 同上 `:807–817` | `detected.x/y`，**z 恒为 0.02，`orientation.w=1.0`** | **硬编码 `0.50 / 0.0`**，z=0.02，姿态单位 |
| `attachObject` 的 object_world_pose | 同上 `:1258–1281` | 先读 PlanningScene 物体，再退回检测位姿 | **硬编码 `0.50 / 0.0 / 0.02`** |
| `executeTransport` 的 dx/dy | 同上 `:1454–1467` | Mode B：`rod_target − detected`，**并限幅** | 固定 `dx=0.12, dy=0.06`（`enable_rotate=true`）或 `0.20/0.10` |
| `executeRotate` 的 `total_angle` | 同上 `:1596–1609` | `rod_target_yaw_rad_ − init_yaw`（**只用 yaw**） | 固定 `M_PI/4`（45°） |
| `executeDescend` 的 `place_z` | 同上 `:1919–1921` | —（与位姿无关） | `place_release_hand_z_ref_`，无效时退回 `grasp_height_` |
| `detachAndReplaceObject` 的杆中心/朝向 | 同上 `:2302–2312` | —（与位姿无关） | 由**双手中点**推算，`z` 硬编码 `0.02`，`rod_yaw = atan2(hand_dy, hand_dx) + π/2` |

**核心事实**【源码证实】：**Mode A（`use_vision=false`）下，任务对杆位姿的认知完全来自硬编码
`(0.50, 0.0, 0.02)` 与单位姿态**，与杆在 MuJoCo 中的实际位姿无关。A1 只要采样出
`(0.50, 0.0)` 以外的位置，PlanningScene、APPROACH、GRASP、attach 就会同时错位。

### 2.2 逐阶段：固定值 / 视觉分支 / 静默限幅

**INIT**（`executeInit`，`:909–961`）
- `:915–934` 视觉分支：`use_vision_` 为真时最多等 10 s 拿 `/detected_rod_pose`，超时 → `ERROR`。

## 3. 坐标系、杆长轴与 yaw、四元数顺序、左右抓取变换

### 3.1 world 与规划坐标系 base_link 的关系

【源码证实】
- `franka_moveit_config/srdf/dual_panda.srdf.xacro:16`：
  `<virtual_joint name="virtual_joint" type="fixed" parent_frame="$(arg parent_frame)" child_link="base_link"/>`，
  `parent_frame` 默认 `world`（`:7`）。
- `franka_description/robots/sim/dual_panda_arm_sim.urdf.xacro:11` `base_link` 为 URDF 根；
  `:31–32` 两臂经 `xyz="0 +0.26 0"` / `xyz="0 −0.26 0"` 接到 `base_link`（`:28–29` 的真机分支被注释）。
- MuJoCo 侧 `mj_dual.xml:138` / `:287` 把 `mj_left_link0` / `mj_right_link0` 直接放在 worldbody 的 `0 ±0.26 0`。

⇒ 在当前模型中 **world 与 base_link 数值对齐**。规划场景里的 `header.frame_id="base_link"`
与 MuJoCo 的 `world` 数值等价。

**这是当前模型的配置假设，不代表 TF 链已经存在。**`world` 由 MoveIt 虚拟关节在内部提供，
`robot_state_publisher` 不会发布 `world→base_link`；而 `SetBodyStateCB`（`ros_api.cpp:206–218`）
在 `frame_id` 非空且 ≠ `"world"` 时会去 MuJoCo 节点的 `tf_buffer_` 查 TF，**查不到就整体失败**。

⇒ **P1a 固定使用 `frame_id="world"`**（不传 `"base_link"`，也不为空）。数值一致性由
“MuJoCo 世界即规划基座”这一假设承担，并在 P1b 用一次真值/PlanningScene 对比来验证。
TF 可用性属于构建期与运行期之间必须实测的项（§9 V4）。

### 3.2 杆的局部长轴、yaw 与四元数顺序

【源码证实】
- 杆局部**长轴 = +Y**：`objects.xml:12` `size="0.02 0.2 0.02"`（半尺寸，中间分量对应 Y）；
  `dual_arm_controller.cpp:797–804` 注释与 `dimensions[1] = 0.40` 一致；`:1325` 同；
  `:2306–2307` 注释明写 “The rod's local long axis is its Y axis”。
- **yaw 不是长轴相对世界 X 轴的角度**。设杆姿态 yaw = θ（绕世界 Z 旋转），则
  `long_axis_world = Rz(θ)·Ŷ = (−sinθ, cosθ, 0)`，
  相对世界 +X 的角度 = **θ + 90°**。阶段计划的警告得到证实。
- `objects.xml:6` 用 `euler="0 0 0"`，`mj_dual.xml:2` 声明 `angle="radian"`；`euler` 只给 Z 分量，
  故等价于 `Rz(yaw)`。一键脚本 Mode B 也按此写入（`start_dual_arm_task.sh:612`），
  `detachAndReplaceObject` 的独立推断（`:2310`）与之自洽。
  【待运行核实】`euler` 的转角序列（MuJoCo 默认 intrinsic xyz）在此只用到 Z，建议 P1a
  用一次 `set_body_state` → `get_body_state` 往返来实测确认，而非仅凭推断。
- **四元数顺序**：MuJoCo 的 `quat`/`qpos` 是 **(w, x, y, z)**，ROS `geometry_msgs/Quaternion` 是
  **(x, y, z, w)**。证据：
  - `mj_dual.xml:237` `quat="0.9238795 0 0 -0.3826834"` = (w=0.92388, z=−0.38268) = 绕 Z 转 −45°，
    与 URDF 的 `rpy="0 0 −pi/4"`（`franka_description/robots/common/hand.xacro` 经
    `dual_panda_arm_sim.urdf.xacro:36` 传入）一致；
  - `mj_dual.xml:261` `quat="0 0 0 1"` = (w=0, z=1) = 绕 Z 转 180°，用于把第二个手指放到另一侧
    （模长恰为 1，是合法四元数）；
  - `ros_api.cpp:221–227`（写）与 `:287–290`（读）显式做 w↔w 映射。

⇒ **任何在 MuJoCo 与 ROS 之间搬运四元数的代码都必须换序**。`/set_body_state` 与 `/get_body_state`
已经处理正确，A1 直接使用即可；但**不要**用 `euler`/`quat` 字符串做通道。

### 3.4 当前的左右抓取变换（A0 语义）与 yaw 泛化

【源码证实】A0 的抓取目标（法兰系，frame = base_link）为：

```
left_flange  = rod_center + (0, +0.15, 0)，orientation = RPY(π, 0, π/4)
right_flange = rod_center + (0, −0.15, 0)，orientation = RPY(π, 0, π/4)
grasp 高度：法兰 z = grasp_height_ = 0.13（APPROACH 用 approach_height_ = 0.28）
```

数值自洽性核对（供 P1a 复核，非运行结果）：法兰姿态 `R = Rz(45°)·Rx(180°)`，其局部 Z 轴
= 世界 −Z；TCP = 法兰 + 0.1034·(局部 Z) ⇒ TCP 在法兰正下方 0.1034。
抓取时 TCP_z ≈ 0.13 − 0.1034 = 0.0266，与杆中心 0.02 基本同高；TCP 的 X/Y 与法兰相同，
故夹持点位于杆长轴上距中心 0.15 处（杆半长 0.20，即距端部 5 cm）。

【源码证实】手指闭合方向为手局部 +Y（`mj_dual.xml` 中 `class="finger"` 的
`<joint axis="0 1 0" type="slide" .../>`，见 `mj_dual.xml` 的 `<default class="panda">` 内）。
手相对 `link8` 为 `Rz(−45°)`，故世界闭合方向 = `Rz(45°)·Rx(180°)·Rz(−45°)·Ŷ = X̂`，
**垂直于杆长轴 Ŷ** —— yaw=0 下几何正确。

**yaw 泛化推导（候选推导，不是已验证结论）**：
把法兰姿态左乘 `Rz(θ)`，即 `R' = Rz(θ)·Rz(45°)·Rx(180°) = Rz(45°+θ)·Rx(180°)`，等价于
`RPY(π, 0, π/4 + θ)`。因为 `Rz(θ)` 不改变世界 Z 轴，法兰局部 Z 仍为世界 −Z（仍是垂直下抓）；
手指闭合方向变为 `Rz(θ)·X̂`，杆长轴变为 `Rz(θ)·Ŷ`，正交性在旋转下保持 ⇒ 仍垂直于长轴。
抓取点偏移同时变为 `rod_center + (±0.15)·(Rz(θ)·Ŷ)`。

**该推导的前提**：杆保持**平躺**（只绕世界 Z 做纯 yaw 旋转），且 §3.4 中对
“法兰姿态”“手相对 link8 的 `Rz(−45°)`”“手指闭合方向 = 手局部 +Y”三处的解读成立。
**降级为候选推导**，不能当作已验证的固定抓取变换。

【待运行核实】以下都必须在**读运行配置之后**确认，而不是由本文件断言：
- 单臂组的末端 link 究竟是 `mj_left_link8` 还是 `mj_left_hand_tcp`
  （由 SRDF 生成结果决定；本文 §3.3 依据 `dual_panda_arm.xacro:6` 判断为 `link8`，需实测确认）。
- `0.15`（夹持点距杆中心）与 `0.13`（法兰抓取高度）是历史经验值，须由手/指几何重新推导，
  并用抓取试运行确认。
- 本推导**不覆盖**非平躺姿态；A1 采样范围只包含平躺 + yaw，故该限制与当前范围一致。

⇒ P1b 的 APPROACH/GRASP 改动方向是“偏移量乘 `Rz(θ)`、姿态 yaw 加 θ”，
但**本轮 P1a 不实现**，且实现前需先完成上述实测确认。

### 3.5 闭链表达的不一致（必须记录）

【源码证实】MuJoCo 里杆被 **同时** weld 到左手与右手（`mj_dual.xml:461`、`:463`），
而 MoveIt 里杆只 attach 到 **一个** link：`mj_left_hand`
（`dual_arm_controller.cpp:1245`，`attachObject`）。

**这不是“attach 写错了”。** MoveIt 中把物体附着到单个 link 是**常规表达**，本身没有问题。
真正的缺口是：**右手与物体之间的相对约束未被表达**，以及**附着状态下杆与右手指/右臂的碰撞处理未明确**
（`touch_links` 覆盖了右手 link，见 `:1240–1242`，但那只解除碰撞，不施加相对位姿约束）。

对 P2/P3 的结论不变但理由更准确：**协调残差必须由实际双手变换计算**，不能引用附着物体模型，
因为该模型并不表达“杆同时受两只手约束”这一物理事实。

## 4. 最小改动的 P1a / P1b 方案

### 4.1 总体链路

```

  → 任务同步 PlanningScene（杆为世界物体）
  → P2 有效性检查
  → 执行
```

`use_vision=false` 全程保持；真值话题与视觉话题**物理分离**。

### 4.2 配置字段（新增 `dual_arm_carry_task/config/a1_scene_sampling.yaml`）

### 4.3 场景应用方式：运行时设置 + 单次写入

**方案 A（P1a 采用）——运行时 `/set_body_state`**

- 调用：`mujoco_ros_msgs/srv/SetBodyState`，`name="obj_rod_01"`，
  `set_pose=true`，`set_twist=true`（twist 全 0），`set_mass=false`，**`reset_qpos=false`**，
  `pose.header.frame_id = "world"`，`twist.header.frame_id = "world"`，
  四元数用 ROS 顺序 `(x,y,z,w)`。
- 依据：`interface.cpp:260` 取 `physics_thread_mutex_`，该段写入与步进互斥（§1.5）。
  **但这只证明该段写入与步进互斥，不能单独证明整个启动、模型重载、服务超时和任务生命周期安全**，
  后者由 §4.6、§4.8 与 §4.9 的检查分别覆盖。
- 优点：**不改任何 XML**，不产生场景副本，不需要处理 2 条 `<include>` 与 `meshdir="assets"`，
  安装树保持唯一真源。
- 已知限制：`set_pose` 与 `reset_qpos` 互斥（`interface.cpp:261–266`），故不能用 `reset_qpos`
  来“复位”；复位应直接 `set_pose` 回 XML 位姿，或调用 `/reset`（整场景复位，会一并复位机器人，
  **A1 不使用**）。

**单次写入规则（新增强制约束）**

1. **每轮只写一次。** 写请求超时、响应失败或状态不明时，**记录并停止本轮**，
   标记为“结果不确定”，**不重试、不重采样写下一候选**。
2. 理由：ROS service 超时**不取消**服务端已接受的调用，旧写请求可能稍后生效；
   且 `SetBodyStateCB` 对 TF 失败的处理是**可能先清零 twist 再返回 failure**
   （`ros_api.cpp:236–251` 先写 `twist`，`:206–218` 的变换失败在 `:230–233` 才把 `set_pose` 置假），
   **响应失败不等于没有副作用**。一旦无法确定杆的最终位姿，后续候选的“初始位姿”就不可信。
3. 写入前必须确认：模型已就绪、杆身份正确、基线状态可读（§4.8）。
4. **每轮使用执行器自行启动的新仿真实例**，禁止对未知的现有会话应用位姿。

**方案 B（备选，本轮不实现）——每轮生成场景副本**

仅当 P1a 实测确认 `/set_body_state` 不可用或行为不符时，才由规划器另行决定退回副本方案。
届时必须：复制 `dual_scene.xml` + `mj_dual.xml` + `objects.xml` + `assets/`（或对 `assets/`
做相对软链）到本轮专属目录，用 `modelfile:=<副本 dual_scene.xml>` 启动，并保证两条 `<include>`
与 `meshdir="assets"` 相对路径仍可解析。**禁止** `sed` 改源码 XML，**禁止**覆盖安装树
（一键脚本 Mode B 现在的做法 `start_dual_arm_task.sh:604–617` 属于禁止模式）。

**本轮遇到服务不可用或行为不符时：停止并报告，不自动切换方案。**

### 4.4 确定性采样与候选编号

**采样必须能独立离线运行**（不依赖 ROS、MuJoCo 或任何服务），因此采样逻辑放在纯函数库里，
可由单元测试直接驱动。

**确定性定义（本方案选择“定义明确的整数到浮点映射”，而非标准库浮点分布）**：

- 对候选 `n` 与通道 `c ∈ {x, y, yaw}`，用 `splitmix64` 生成 64 位整数流：
  以 `v0 = splitmix64(seed ^ (n * 0x9E3779B97F4A7C15) ^ (c * 0xBF58476D1CE4E5B9))` 为起点，
  每个通道取一个 64 位值 `v`。
- 映射到 `[0, 1)`：`u = (v >> 11) * 2^-53`（双精度，**完全由整数运算定义**）。
- `value = lo + u * (hi - lo)`。
- **不使用** `std::uniform_real_distribution` / `std::mt19937` 的浮点输出。
  理由：标准库未规定 `uniform_real_distribution` 的具体算法，跨 libstdc++/libc++/版本
  可能产生不同序列；上面的映射只依赖整数运算与 IEEE-754 双精度，跨标准库可复现。

**确定性契约**：**同一 `seed` + 同一 `candidate_index` + 同一完整配置（含所有范围字段）
+ 同一 `algorithm_version` ⇒ 同一候选位姿**。

- 记录**完整配置 hash**，而不是只记 `sampling_range_version`：hash 覆盖全部影响采样的字段
  （seed、x/y/yaw 范围、几何、`algorithm_version` 等），算法为 **FNV-1a 64 位**，
  并同时把**规范化字符串**写进清单，使 hash 可被独立复算。该 hash 是**变更检测校验和**，
  不是密码学摘要，清单中明确标注。
- 记录**请求 seed** 与**实际使用的候选编号**，两者分开。
- `max_total_candidates` 限制单轮总候选数；本轮 `max_write_attempts_per_run = 1`
  （见 §4.3 单次写入规则），因此本轮**不会**出现“写失败后换下一候选”。
- 不做“抓取失败后重采样并把失败抹成场景拒绝”：本轮不执行抓取；P2 之后，拒绝只发生在
  有效性检查未通过时，接受之后执行失败一律计入失败（P2/P6 口径）。

### 4.6 稳定判据（重写）

上一版“25 个 20 ms 样本”的判据**不成立**：轮询次数不等于仿真进展，仿真暂停时重复读数
也会满足“相邻增量很小”；0.5 mm/20 ms 也可能接受明显的慢漂移。新判据要求：

**必要条件（全部满足才算稳定，任一不满足即不判成功）**

1. **仿真时钟有效且持续前进**：节点时钟（`use_sim_time=true`）在每个样本都有效，
   且相邻样本的仿真时间**严格递增**；出现回跳 → `E_CLOCK_JUMP`，**直接停止本轮**。
2. **窗口有最小仿真时长**：窗口首尾的**仿真时间**差 ≥ `min_sim_window_sec`。
3. **仿真时间与 wall(steady) 时间推进比例合理**：
   `sim_window_sec / steady_window_sec >= min_clock_advance_ratio`，
   用于排除“wall 时间在走但仿真暂停/极慢”的情况。
4. **整窗（不是相邻）位置与姿态变化受限**：
   `max_i‖p_i − p_ref‖ <= max_window_pos_tol`、
   `max_i angle(q_i, q_ref) <= max_window_angle_tol_deg`，
   其中 `p_ref/q_ref` 取窗口内**中位数样本**（对少量离群抖动稳健）。
5. **有效 twist 范数受限**：窗口内所有样本的 `‖twist.linear‖ <= max_twist_linear_tol`、
   `‖twist.angular‖ <= max_twist_angular_tol`。
   若服务返回的 twist 无效（非有限值），该样本**作废**，窗口不成立。
6. **静止几何判据**：末样本 `|z − (support_surface_z + rod_half_height)| <= resting_z_tol`
   且 `|roll|,|pitch| <= resting_tilt_tol_deg`。

**超时**：使用 **steady-clock** 计时，超过 `stability_timeout_sec` → `SCENE_SETTLE_FAILED`，
原因码 `E_SCENE_SETTLE_TIMEOUT`，**停止本轮**（不换候选，见 §4.3）。

**暂停、时钟回跳、模型重载一律不能输出成功。** 模型重载通过
`get_sim_info` 的 `load_count` 在轮询期间变化来检测 → `E_MODEL_RELOADED`。
`sim_info.paused` 为真时不得判成功。

**重要限定**：“落地高度/倾角合理”只是**静止几何判据**，
**不能证明杆与支撑面之间存在真实接触**（也可能静止地悬在别处）。
本轮不声称证明了接触或放置质量。

旋转距离使用 `q` / `−q` 等价的姿态距离：`d = 2·acos(min(1, |dot(q1,q2)|))`。

### 4.7 真值接口与冻结时机（P1b 修订设计，本轮不实现）

**先修正一个事实错误**：上一版用 “`stamp` 必须晚于任务 `INIT`” 做新鲜度判断，**不可行**。
`GetBodyStateCB` 在 `ros_api.cpp:282` 与 `:292` 用**默认构造**的 `std_msgs::msg::Header`
（只填 `frame_id`），**返回的 `stamp` 恒为零**。因此：

- **不得**用 `/get_body_state` 返回的 `stamp` 做任何新鲜度、顺序或时效判断。
- P1a 记录的是**请求/响应的 steady-clock 区间**与**请求/响应时刻的 ROS 仿真时间**，
  作为该次交互的时间证据；**不伪造精确的物理采样时刻**（服务不提供该信息）。
- 若需要更强的时间证据，应由 **P2 阶段另行的真值节点**主动打时间戳（它自己知道何时读的），
  而不是引用服务端 `stamp`。

**启动时序冲突（上一版方案自相矛盾之处）**：上一版要求“先准备场景、后启动任务”，
又要求“`stamp` 晚于 `INIT`”，两者无法同时满足 —— 先发会被判旧；
而 writer 进程退出后 `transient_local` **不保证**后来的订阅者还能拿到历史样本。

**P1b 修订设计（需单独审阅，本轮只提出设计）**：

- 采用 **`run_id` 握手 + 生命周期契约**，而不是依赖消息 `stamp`。
- **关键限制**：**两个独立的 latched 话题不能保证原子配对** ——
  订阅者可能先看到 `run_id` 而拿不到位姿，或反之，甚至跨 run 交错。
  因此正确的做法是**把 `run_id` 与位姿放在同一条消息里**（例如自定义消息，
  或在同一条 `PoseStamped` 上通过 `frame_id` 之外的字段承载），
  使“哪一轮的位姿”随位姿本身原子到达。
- 契约：真值发布者**在任务启动之前**完成发布并**保持自身存活**至本轮结束
  （否则 `transient_local` 的历史对后来的订阅者不保证可见）；
  任务节点在 `INIT` 读**一帧**并**冻结**，此后不再更新。
- `stamp` 字段即使填写，也**只作为发布者本地的参考信息**，不作为接收方的判据。

**为何不让真值复用 `detected_rod_pose_` 但加旗标**：`carry_task_context.hpp:110–131` 的
`rod_pose_received_` 一旦置真**永不失效**，且没有时间戳与来源信息，无法表达“冻结”与“陈旧”。
因此 P1b 必须新增独立的存储与有效性字段，而不是复用一个已有 3 个入口在用的共享槽位。
**本轮 P1a 完全不发布真值话题。**

## 5. P2 有效性检查：实现位置、所需接口、与 ACM 的关系

### 5.1 与“初始位姿检查”和“完整搬运路径验证”的区别

- **P2（本阶段）**：只判断**这个样本能否进入执行**。第 5 项“联合预抓取路径”只覆盖

### 5.4 ACM 是否掩盖必要碰撞：是，且有具体条目

【源码证实】

- SRDF 中大量 `disable_collisions`（`dual_panda.srdf.xacro:82–149`）包含：
  - `reason="Never"`：如 `mj_left_link0`↔`mj_right_link1`（`:87`）、
    `mj_left_link1`↔`mj_right_link1`（`:90`）、
    `mj_left_link4`↔`mj_right_hand`（`:134`）、`mj_left_link5`↔`mj_right_hand`（`:139`）、
    `mj_right_link4`↔`mj_left_hand`（`:144`）等 —— 这些是**双臂之间**的配对，
    “Never 碰撞”在双臂协作里是强假设。
  - `reason="User_Allowed_Collision"`：`mj_left_link5`↔`mj_right_link2`（`:119`）、
    `mj_left_link5`↔`mj_right_link6`（`:126`）、`mj_left_link6`↔`mj_right_link5`（`:127`）。
  - `reason="Adjacent_Arms"`：`mj_left_link2..5` × `mj_right_link2..5` 的整片区域（`:101–122`）。
- `initializeCollisionMatrix()`（`dual_arm_controller.cpp:519–686`）**当前未被调用**
  （`executeInit:947–949` 已禁用，注释明写“不再手动初始化 ACM”）。
  所以运行时生效的是 **SRDF 的默认 ACM**。
- 运行时对 ACM 的**唯一**修改是 `allow_gripper_collision`（`:688–783`），它
  1. 取回完整 ACM（`:693–716`），
  2. 只改 6 个夹爪 link 与 `"aluminum_rod"` 的条目（`:719–753`），
  3. 以 `is_diff=false` 发回**完整** ACM（`:764–766`）。
  ⇒ 这一步**保留**了上述所有 SRDF 禁用项。

⇒ **P2 第 4 项检查必须把“实际使用的 ACM”和“被禁用的具体配对”一并记录到运行清单**，
否则无法区分“确实无碰撞”和“碰撞被 ACM 关掉了”。

**对照检查的正确方向是收紧 ACM，而不是放宽。** 上一版写“放宽 ACM 的对照检查”是错的：
“放宽”即允许更多碰撞对，只会让检查更宽松、更容易漏掉真实碰撞，无法量化掩盖程度。
正确做法是**收紧 ACM**：对上述非必要禁用项（尤其 `reason="User_Allowed_Collision"` 与
跨臂 `"Never"`）**重新启用碰撞检查**，再跑同样的位姿序列；
两组结果的差集就是被 ACM 掩盖的碰撞。该对照仅作**诊断**，不改变正式运行配置，
且必须在清单中同时记录“正式 ACM”与“诊断 ACM”。

## 6. 对 A1 构成实际阻塞的问题（分级，本轮不修）

**B1 — 阻塞级（挡 P2 第 2 项与 P3）**

在当前启动链中未见与视觉分离的真值入口；`rod_pose_received_` 一旦置真永不失效、
无时间戳无来源（`carry_task_context.hpp:110–131`）。
**归属：P1b 真值接入（`run_id` 握手 + 冻结 + 生命周期契约，见 §4.7）。**

**B3 — 阻塞级（挡可复现性与 A1 入口）**
- 无 `run_id`/seed/manifest 记录机制。

## 8. 关键发现（供规划器审阅）

1. **真值通道已经存在，且是安全的**：`/get_body_state` 与 `/set_body_state`
   （`mujoco_ros`，根命名空间）已提供杆位姿读写，`SetBodyState` 取
   `physics_thread_mutex_`（`interface.cpp:260`），是唯一被证实与 `mj_step` 互斥的写入路径。
   **A1 不需要新增任何 C++ 服务端，也不需要场景副本。**
2. **绝不能在 ROS 回调里直接写 `d_->qpos`**：`franka_mj_hardware_system.cpp` 里没有任何
   mutex（`:356` 的 `lock_guard` 已注释且 `mj_mutex_` 不存在），会与物理线程竞争。
3. **world ≡ base_link** 已由虚拟关节（SRDF xacro:16）与两侧 `±0.26` 基座布置证实；
   但 **`world` 未必在 `/tf` 上**，所以 `set_body_state` 的 `frame_id` 应留空或写 `"world"`，
   写 `"base_link"` 会触发一次可能失败的 TF 查询。
4. **四元数顺序 w-在前 vs w-在后**：MuJoCo `quat`/`qpos` 是 `(w,x,y,z)`，
   ROS 消息是 `(x,y,z,w)`；`set/get_body_state` 已正确处理，但任何自建通道都必须换序。
5. **杆局部长轴是 +Y，且“yaw ≠ 长轴相对世界 X 的角度”**：两者差 90°。
   阶段计划的警告在源码中得到确认。
6. **A0 的抓取目标完全不随杆 yaw 旋转**（`:1000–1019`），且 Mode A 下位姿认知是硬编码
   `(0.50, 0.0, 0.02)`。这是 A1 最核心的改动点；泛化式子是
   `偏移 × Rz(θ)`、`姿态 yaw + θ`（推导见 §3.4，几何上自洽）。
7. **0.64 kg 的来源已定位**：`objects.xml:12–13`，box 体积 6.4e-4 m³ × density 1000。
   本轮保持，0.5 kg 修正单列。
8. **现有“轨迹校验”不含环境碰撞**：`validateManualTrajectory` 用裸 PlanningScene +
   默认 ACM + 仅自碰撞（`:240–260`），且**支撑面在 PlanningScene 中根本没有对象**。
9. **ACM 确实掩盖碰撞**：SRDF 中有成片的双臂间 `Never` / `Adjacent_Arms` /
   `User_Allowed_Collision` 禁用（`dual_panda.srdf.xacro:101–149`），
   而运行时只增补“夹爪↔杆”条目、不改动这些（`:688–783`）。
10. **物体放置误差当前无法计算**：释放后从不读回杆真值，现有 `ee_terminal_error_mm` 是
    用近似常量重建期望点的**末端**误差（`task_metrics_monitor.cpp:435–438`）。
11. **一键脚本不适合 A1**：需要交互输入、会写源码树（XML 与 SRDF）、会用宽泛 `pkill -9 -f`。
12. **柔顺参数受环境变量控制**，脚本值与 C++ 内建默认不同
    （`MIN_K 0.45 vs 0.10`、`MAX_D 1.80 vs 2.5`），必须逐轮记录。

## 10. P1a 的修改范围与验收

**P1a 只做“配置、采样、场景应用”，并且只验收这条链：**
**候选 → 仿真应用 → 稳定读回 → 清单**。

交付：

1. `dual_arm_carry_task/config/a1_scene_sampling.yaml`（§4.2 字段）。
2. `a1_sampling.hpp` / `a1_sampling.cpp`：**纯逻辑、可离线测试** ——
   确定性采样（splitmix64 + 整数→浮点映射）、footprint 几何、稳定判据求值、
   单候选编排状态机（通过抽象 transport 注入，便于故障注入测试）。

   实现 transport（`/set_body_state`、`/get_body_state`、`/get_sim_info`）、
   有界轮询、**只写清单，不发布真值话题、不启动任务**。
4. `scripts/a1_run_scene.sh`：非交互；支持 `--dry-run` 与单候选应用；
   显式 `--candidate-index` 与 `--run-id`；**不做批量任务**；
   脚本拥有其启动的进程，退出时只向**自有 PID/进程组**发 SIGINT 并回收；
   **禁止 `pkill`/`killall`**；记录明确的 ROS 会话隔离方式。
5. `CMakeLists.txt` / `package.xml`：新增真实使用的依赖（含 `mujoco_ros_msgs`）、
   库与可执行目标、config 安装、测试目标。**不安装新依赖**；缺失即报告。
6. `test/`：采样确定性、非法输入、四角几何、`q`/`−q` 姿态距离、
   稳定判据负例（暂停重复读数、慢漂移、时钟回跳、仿真窗口不足）、
   服务故障注入（不可用 / 失败 / 超时 → 不再次写入 + 留清单）。
7. `docs/deliverables/A1_P1a_验证记录.md`：命令与结果、manifest 样例与数据路径、
   失败记录、遗留问题、以及“A0 未破坏现有入口”的证据。

**不得填 `accepted=true`**，不记 `p2_acceptance`、不记任务结局、不记放置误差（一律 `null`）。

**验收范围（收敛后的版本）**：同 seed + 同候选 index + 同一完整配置 + 同一 `algorithm_version`
