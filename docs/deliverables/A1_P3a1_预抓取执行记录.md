## B. 修复一：超时异步生命周期

**原问题**：worker 以 `[&]` 捕获栈上的 `exec_code`；超时 `stop()` 后若仍未结束就 `detach()`，
迟到结果会写入已失效的栈对象，也可能访问已销毁的控制器。

**修法**：把“有界等待 + 迟到结果安全”抽成可离线测试的 `a1v::runBoundedExec(...)`：
- worker 只捕获**共享状态**（`shared_ptr<atomic<int>>` 结果槽、`shared_ptr` 结果/异常标志）
  与**按值**捕获的可调用对象 —— **不捕获裸 `this`、不引用栈对象**；
- 控制器另以 `std::shared_ptr<MoveGroupInterface>` **按值**捕获接口本身，
  保证调用在飞行期间接口不会被销毁；Plan 也按值复制；
- 超时后调用 `on_timeout`（即 `stop()`），再等 `grace_sec`；
  **记录**是否发出停止请求、worker 是否在宽限期内结束；
- worker 若仍未结束则 `detach` —— 此时**安全**（其捕获全部是共享状态）；
- **迟到成功永不参与判定**：`runBoundedExec` 对迟到结果仍返回 `TIMEOUT`，
  控制器在该分支直接 `return false`，不回读结果；不重试、不继续；
- 执行抛异常归类为 `EXCEPTION`（失败），不当作完成；
- 不使用无限 `join` 掩盖有界等待：等待窗口由 `pregrasp_exec_timeout_sec` 界定。

关于“优先复用受管理的异步 action”：`MoveGroupInterface` 提供了 `asyncExecute()`，
但**不暴露**其内部轨迹执行 action 的 goal handle，外部无法取得结果 future；
若自建 action 客户端则要自行拼装 `MotionPlanRequest`，反而更易出错。
因此按提示词允许的备选路径（保留工作线程 + 保证生存期）实现，并**显式**保证结果、Plan、
接口所有者三者的生存期。

## C. 修复二：最终下发轨迹的速度/加速度校验

新增 `a1v::checkDerivativeField(...)`，**下发前**逐一检查每个航点的
`velocities` / `accelerations`：

| 情形 | 处理 |
|---|---|
| 分量非有限 | 拒绝（`E_DERIV_NOT_FINITE`） |
| 维数与关节名不符 / 字段存在但为空 | 拒绝（`E_DERIV_DIM_MISMATCH`） |
| 超出**实际声明**的限制 | 拒绝（`E_DERIV_LIMIT_EXCEEDED`） |
| 某关节**未声明**限制 | **跳过并计数**，不当零、不声称达标 |
| 只有部分点带该字段 | 拒绝（`E_TRAJ_VELOCITY/ACCELERATION_INCONSISTENT`） |
| 全部点都**缺**该字段 | **显式告警**“该限制未被校验，不据此声称达标”，不当零 |

**限制来源**：`live` 模型（`ctx_->dual_arm_->getRobotModel()`），即加载了
`robot_description_planning`（`joint_limits.yaml`）的那一个 —— **不编造限制**。
这里发现一个实际问题：P2a 的独立判据模型只由 URDF+SRDF 构造，
**不含加速度限制**，若用它取限制会把加速度校验静默变成空操作
（实测会报 94×14=1316 个关节“未声明限制”）。两模型关节限制相同，
仅手掌碰撞几何不同，故改用 live 模型取限制并在日志中标明来源。

**实测（`a1_p3a1_fix_yawp10g`）**：


# 追加：P3a-1 有界执行结果的 deadline 顺序（2026-10-13）

仅修 `a1v::runBoundedExec` 的 deadline 判定顺序及相关测试。**未重复预抓取仿真、未下降、未操作夹爪、未提交 Git。**

## A. 更正上一轮的说明

上一轮我写“迟到成功永不参与判定：`runBoundedExec` 对迟到结果仍返回 `TIMEOUT`”。
**该说明当时并不成立**——实现里等待循环退出后只看“结果槽是否已写入”，
**没有区分结果是在 deadline 之前还是之后到达**。若 worker 在预算耗尽之后、
下一次轮询醒来之前完成，循环醒来时槽已写完，就会被**误判为 `COMPLETED`**。
规划器用生产纯逻辑离线复现（放大轮询边界）：

```
（修复前）timeout_budget=0.010 work_delay=0.025 poll=0.050
completed=1 timeout=0 elapsed=0.0501034 stop_requested=0
```

共享生存期本身是安全的（那部分无需重做），缺陷只在**判定顺序**。

## B. 修法：按 worker 自己的完成时刻判定

- worker 在完成时把**自身完成的 steady-clock 时刻**（相对 `begin` 的纳秒数）写入共享槽，
  并且**最后**发布该时刻，因此“时刻可见”即蕴含“结果已写入”，无锁、无竞态窗口。
- 等待循环改以该时刻判断“是否仍在运行”，不再用结果槽代替。
- 循环结束后**一律按完成时刻与预算比较**：
  - `finished <= budget` → `COMPLETED`（**即使轮询很晚才观察到**，及时完成不会被误判为超时）；
  - `finished > budget` → **`TIMEOUT`**（**即使结果槽此时已经写完**，迟到成功仍只算超时）。
- 只有**仍在运行**的 worker 才会请求停止；**已经结束的迟到结果不再发停止请求**，状态仍为 `TIMEOUT`。
- `begin` 在**创建 worker 之前**取得，顺序明确：`begin → 预算/deadline → 启动 worker`；
  worker 按值接收 `begin`。保留了原有的按值捕获与共享对象生存期，未加锁框架、未用无限 join。
- 结果新增 `completed_at_sec` / `timeout_sec` 两个字段，供判定与记录。

## C. 修复后同一复现

```
timeout_budget=0.010 work_delay=0.025 poll=0.050
completed=0 timeout=1 elapsed=0.0501 stop_requested=0
late_value_kept_for_diagnostics=1 completed_at=0.0252 budget=0.0100 worker_finished=1
```

`completed` 由 1 变为 **0**、`timeout` 由 0 变为 **1**：迟到结果现在被正确判为超时；
`completed_at=0.0252 > budget=0.0100` 正是判定迟到的依据；
`stop_requested=0` 是因为 worker 已自行结束，无需（也不应）再请求停止。
执行侧在该分支直接 `return false`，**迟到结果不参与判定，不会变成 `PREGRASP_REACHED`**。

## D. 新增/保留的针对性测试

`test_a1_sample_validator` 46 → **48**，`A1SampleBoundedExec` 共 **7** 例：

| 用例 | 断言 |
|---|---|
| **worker 超时完成却早于下一次轮询醒来**（0.010/25 ms/0.050） | `TIMEOUT`；`completed_at > timeout`；`elapsed > completed_at`（观察晚于完成）；**未**请求停止、`stops==0` |
| **worker 及时完成但观察较晚**（1.0/5 ms/0.200） | `COMPLETED`；`completed_at <= timeout`；`elapsed > completed_at`；未请求停止 |
| 按时完成 / 抛异常 / 迟到成功 / 超出宽限期安全 detach / 零超时有界 | 保留 |

后两条断言正是本次修复的两个方向：既不能因为轮询晚而把**及时完成**误判为超时，
也不能因为槽已写完就把**迟到成功**当成成功。

按提示词“已结束的迟到结果无需额外停止”改正为 `stop_requested=false`、`stops==0`——是测试写错，不是实现错。
